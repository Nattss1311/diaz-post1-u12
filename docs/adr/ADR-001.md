# ADR-001: Capas simples para persistencia; el seam de notificacion ya cubre el proximo cambio conocido

## Estado: Aceptado — 2026-11-06

## Contexto
Tras integrar Chain of Responsibility, Strategy y Observer sobre el
sistema de solicitudes de reembolso, corresponde decidir si el
proyecto debe migrar a arquitectura Hexagonal completa (puertos e
interfaces intermedias para persistencia y notificacion) o mantenerse
en capas simples. No existe hoy ningun plan de cambiar el motor de
base de datos. Contabilidad si anuncio, para el proximo trimestre,
una integracion por API externa para el pago de solicitudes aprobadas.

## Criterio de evaluacion (Guia, seccion 6.2)
La Guia indica que Hexagonal vale la pena "en sistemas que sobreviviran 3
anos o mas con cambios de infraestructura". Ambas condiciones deben
cumplirse, y se evaluan por separado para cada dependencia externa:

| Dependencia | Sobrevive 3+ anos? | Cambio de infraestructura real y documentado? | Se cumple el criterio? |
|-------------|--------------------|-----------------------------------------------|------------------------|
| Persistencia (JPA/H2) | Probable: reemplaza una hoja de calculo de uso permanente | No: no existe ningun plan de cambiar el motor de base de datos | No |
| Notificacion a Contabilidad | Probable | Si: integracion por API externa anunciada para el proximo trimestre | Si, pero el seam ya existe (ObservadorCambioEstado) |

## Decision
Se mantiene arquitectura en capas simples para la persistencia:
SolicitudReembolsoService sigue dependiendo directamente de
RepositorioSolicitudesJpa, sin una interfaz de puerto intermedia. Un
puerto de persistencia hoy seria una abstraccion especulativa (YAGNI)
sin ningun caso de uso que lo requiera. Para la notificacion no se
introduce ningun cambio: ObservadorCambioEstado ya es el seam
necesario, y NotificadorContabilidad puede reemplazar su
implementacion interna por una llamada a la API externa el proximo
trimestre sin modificar SolicitudReembolsoService ni los demas
observadores.

## Alternativas consideradas
1. Hexagonal completa: puerto RepositorioSolicitudes + adaptador JPA y
   puerto de notificacion explicito. Descartada para persistencia: no hay
   un segundo motor de base de datos previsto, asi que el puerto tendria
   una unica implementacion (falla la Rule of Three y YAGNI).
2. Hexagonal solo para notificacion (nuevo puerto ServicioPagosExterno).
   Descartada: ObservadorCambioEstado ya cumple el rol de puerto; agregar
   otra interfaz duplicaria la abstraccion sin aislar nada nuevo.
3. Capas simples con el seam de Observer existente. ELEGIDA: cubre el
   unico cambio de infraestructura con fecha conocida sin clases nuevas.

## Consecuencias
Positivas:
- No se agregan interfaces ni mappers de persistencia sin un caso de
uso real que los justifique.
- El unico cambio de infraestructura con fecha conocida (integracion
de Contabilidad) ya tiene su punto de extension listo.

Negativas:
- Si en el futuro se necesita cambiar de motor de base de datos, el
puerto de persistencia debera introducirse retroactivamente; se
acepta esa deuda tecnica de forma consciente.
- Un revisor que espere simetria total (puertos en todas las
dependencias externas) puede interpretar la asimetria como
inconsistencia si no lee este ADR.
